# Camera Demo

Учебный C++17 проект. Конвейер читает mock или видеофайл, передаёт кадры заглушке
обработки и сохраняет timestamp и размеры в CSV. Файловый декодер выдаёт CUDA-кадры;
отдельный режим кодирует CUDA-кадры в H.264 MP4 через NVIDIA NVENC.

## Сборка и запуск

Требуются CMake 3.20+, компилятор C++17, OpenCV (модуль core), pkg-config
и development-пакеты FFmpeg: libavformat, libavcodec, libavutil.
FFmpeg подключён к сборке. `FileVideo::init(path)` открывает файл и находит
видеопоток; рабочий поток декодирует CUDA-кадры и передаёт их через ограниченную очередь.

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
./build/camera_demo build/mock_frames.csv
```

Для существующего видеофайла: `./build/camera_demo --inspect path/to/video.mp4`.
Вывод: индекс видеопотока, codec, размеры и time base. Ошибка открытия или
отсутствие видеопотока завершают программу с кодом 1. Файловая реализация также
создаёт CUDA-контекст на устройстве 0: нужен доступный NVIDIA GPU и драйвер.
В песочнице доступ к GPU может быть запрещён. При `--inspect` проверяется
поддержка CUDA выбранным decoder, копируются параметры потока
и открывается decoder с CUDA-контекстом. Callback `get_format` допускает только
CUDA-поверхности. Подтверждение аппаратного декодирования конкретного видео
потребует чтения кадров: часть инициализации выполняется только после подачи packets.
Без GPU открытие завершается ошибкой, автоматического CPU fallback нет.
Команда `./build/camera_demo --decode-first path/to/video.mp4` служит отдельной
диагностикой первого CUDA/GPU-кадра. Полный сценарий:
`./build/camera_demo --decode path/to/video.mp4 decoded.csv`. Декодирование требует
GPU; CPU fallback и перенос кадров на CPU не выполняются.
Для перекодирования: `./build/camera_demo --transcode path/to/input.mp4 output.mp4`.
Нужны CUDA-декодер и FFmpeg encoder `h264_nvenc`, доступные NVIDIA GPU/драйвер и
CUDA hw_frames_ctx, принимаемый encoder. CPU fallback отсутствует. Поток не содержит
аудио. Для каждого кадра обязателен timestamp и положительная duration; они берутся
из декодера. Если timestamp повторяется или идёт назад, MP4 writer сдвигает его к
предыдущему выходному PTS плюс одну микросекунду; например, первый timestamp и шесть
повторов при исходном времени 0 дадут выходные PTS 0, 1, …, 6 мкс. Это сохраняет порядок кадров, но не восстанавливает
их реальное время. Writer считает отсутствующий timestamp ошибкой; CLI при RTSP-записи
пропускает начальные кадры без timestamp. Исходный кадр и его
timestamp не изменяются. Цветовые параметры входного кадра передаются в выходной
MP4 вместе с CUDA-поверхностью; изображение не копируется в CPU. Nominal frame rate encoder выводится из duration первого
кадра; переменные timestamp и duration сохраняются отдельно для каждого кадра.
Сессия записи должна
заканчиваться `Writer::finish()`: деструктор освобождает ресурсы, но намеренно не
пытается дописать незавершённый MP4.

## Три объекта в main

- `Video` читает кадры. Единственный интерфейс; `createMockVideo()` скрывает
  конкретный класс и возвращает `unique_ptr<Video>` — владельца видеовхода.
  Файловая реализация объявлена в `file_video.hpp`, методы — в `file_video.cpp`.
  В main она создаётся явно через `make_unique<FileVideo>()`, затем вызывается
  `init(path)`. Конструктор пустой. `init()` пишет сообщение об успехе или ошибке
  и возвращает bool; main проверяет результат. При ошибке
  освобождаются частично созданные ресурсы, попытку можно повторить.
  Повторный init уже подготовленного объекта возвращает false, сохраняя его состояние.
  `description()` возвращает параметры; `read()` выдаёт CUDA frame с собственным
  временем жизни.
- `Processor::process(Frame&)` пока ничего не меняет.
- `Writer` сохраняет метаданные в CSV или H.264 MP4. Отдельный объект позволяет
  независимо выбирать источник и место записи; MP4 encoder находится внутри writer.

`FileVideo::init(path, std::chrono::seconds(5), 8)` задаёт срок ожидания I/O
(по умолчанию 10 секунд) и глубину очереди (по умолчанию 8). Ожидание ограничено
отдельно для открытия, определения потоков и получения кадра рабочим потоком.
RTSP использует TCP. `requestStop()` можно вызвать из другого потока:
внутренний атомарный флаг проверяет FFmpeg interrupt callback. Рабочий поток
закрывает очередь после EOF, ошибки или остановки. Деструктор запрашивает остановку
и вызывает join до освобождения ресурсов FFmpeg; объект должен жить до завершения
всех внешних вызовов. Методы потребителя вызываются последовательно.

`Frame` содержит CPU `image` либо GPU `gpuImage` (разделяемое владение FFmpeg
`AVFrame`), и необязательный timestamp в микросекундах. Производители заполняют
ровно одно представление; копия Frame сохраняет GPU поверхность после следующего
чтения и уничтожения Video. Отсутствующий timestamp остаётся пустым. Mock выдаёт
пять изображений 4×2 с шагом 40 мс.
`read()` немедленно возвращает `optional<Frame>`: кадр либо временное отсутствие
кадра. `isFinished()` означает завершение источника и опустевшую очередь.
Ошибки рабочего потока передаются через `read()` после выдачи накопленных кадров.
Кадр сохраняет владение своей памятью после следующего чтения. EOF файла остаётся
стабильным после однократной отправки drain-сигнала decoder.

`Writer::init(path, format, queueDepth)` открывает CSV или MP4 output; encoder создаётся при
первом кадре, поскольку только тогда известны CUDA surface и размеры. `finish()`
явно записывает trailer и закрывает файл, чтобы обнаружить ошибки. CSV не содержит
изображения и не является видеофайлом.

## Развитие

В `include/camera/` — объявления, в `src/camera/` — реализации, в `apps/` — main,
в `tests/` — проверки. Временные файлы — в `tmp/`, сборка — в `build/`.
Открытие через libavformat находится в `src/camera/file_video.cpp`; отдельной
диагностической программы нет. Режим `--inspect` использует тот же интерфейс `Video`.

Основной сценарий остаётся простым: `Video` читает кадры, `Processor` обрабатывает
их, `Writer` сохраняет результат; decoder и encoder скрыты внутри соответствующих
классов. Фазовые методы разделяют настройку источника, чтение и завершение записи.

Для изучения pipeline читай код в таком порядке:

1. `apps/main.cpp`: создание `Video`, `Processor`, `Writer` и общий цикл кадров.
2. `FileVideo::init()`: `openInput()` → `createCudaDevice()` → `openDecoder()`.
3. `FileVideo::readerLoop()` вызывает `decodeFrame()`: получение кадра, при необходимости
   `feedDecoder()`, оформление через `makeFrame()` и добавление в очередь.
   Публичный `read()` забирает самый старый из оставшихся кадров.
4. `Writer::writeVideo()`: проверка кадра, открытие encoder/header при первом кадре,
   `prepareEncoderFrame()` → отправка encoder → `drainPackets()` в MP4.
5. `Writer::finishVideo()`: сигнал конца кадров, оставшиеся пакеты, trailer, закрытие файла.

Локальные `Mode` и `Command` в приложении описывают только режим и пути из командной
строки. Они заменяют независимые флаги CLI и не участвуют в передаче видеокадров.

Опциональная интеграционная проверка требует GPU, FFmpeg с `libx264` и `h264_nvenc`,
а также Python 3. Она создаёт воспроизводимые MP4 fixtures и проверяет транскодирование,
PTS, длительность, цветовые метаданные и полное декодирование результата. По умолчанию
она выключена и не добавляет зависимостей к CPU-тестам:

```sh
cmake -S . -B build-gpu-tests -DCAMERA_ENABLE_GPU_TESTS=ON
cmake --build build-gpu-tests --parallel 2
ctest --test-dir build-gpu-tests -L gpu --output-on-failure
```

Fixture и выходные файлы остаются в `tmp/gpu_pipeline_tests/`.

В той же GPU-сборке на Linux доступна проверка сетевых отказов:

```sh
ctest --test-dir build-gpu-tests -R '^rtsp_faults$' --output-on-failure
```

Тест создаёт локальный RTSP/TCP-источник с H.264 и проверяет отсутствие новых данных,
разрыв TCP, переподключение, исчерпание попыток и Ctrl+C во время ожидания.
Проверяется и восстановление после неудачного первого открытия источника.
Нужны доступ к GPU и loopback-сокетам;
ферма, SSH-туннель и дополнительные Python-пакеты не требуются. Проверяются код
завершения, ограниченное время остановки и полное декодирование полученных MP4.
Логи, видео и измерения находятся в `tmp/rtsp_fault_tests/`; тест ограничен 120 секундами.
Неожиданный EOF RTSP считается ошибкой чтения, EOF файла — штатным завершением.

`FrameQueue` — потокобезопасная очередь с глубиной, заданной при создании:

```cpp
camera::FrameQueue frames(8);
frames.push(std::move(frame));
auto nextFrame = frames.pop(std::chrono::milliseconds(100));
```

Нужен header `camera/frame_queue.hpp`. При переполнении удаляется старейший кадр;
`droppedCount()` считает вытеснения. `pop()` без аргумента не ждёт, с таймаутом
ждёт поступления кадра или закрытия очереди. `nullopt` означает отсутствие кадра:
`isClosed()` отличает закрытую очередь от истечения ожидания. `close()` запрещает
новые кадры, будит ожидающих и оставляет накопленные кадры для чтения. Глубина
должна быть положительной. Все потоки, использующие очередь, нужно завершить до
её уничтожения. Проверка: `ctest --test-dir build -R frame_queue --output-on-failure`.

Очередь чтения подключена внутри FileVideo, Processor работает в main. Глубину
можно задать перед режимом: `./build/camera_demo --queue-depth 4 --transcode input.mp4 output.mp4`.
При переполнении удаляются старейшие кадры, в том числе при чтении файла быстрее
обработки; это режим актуальных кадров, а не гарантия сохранения каждого кадра.
Ctrl+C завершает текущую итерацию, запрашивает остановку чтения и дописывает MP4.

Writer также поддерживает отдельный поток и ограниченную FIFO-очередь. В CLI она
включена с глубиной 8; `--write-queue-depth N` меняет глубину, `0` возвращает
синхронную запись. При переиспользовании библиотеки третий аргумент `Writer::init`
по умолчанию равен 0. `write()` принимает кадр в очередь без копирования пикселей;
его содержимое после передачи менять нельзя. `finish()` закрывает приём, ждёт
записи принятых кадров и join, затем дописывает trailer. Деструктор выполняет join,
но не заменяет явный finish для MP4.
Первый MP4-кадр однократно ждёт настройки encoder в worker; это не даёт стартовому
буферу RTSP заполнить очередь во время открытия NVENC. Следующие кадры передаются
без ожидания кодирования.

Для записи используется `FrameQueue::tryPush()`: полная очередь отклоняет кадр
с явной ошибкой, сохраняя уже принятые. CLI завершает принятую часть записи и
останавливается с кодом 1. Ошибки worker передаются через следующий write или finish.
Для GPU FileVideo резервирует буферы и под очередь Writer. Проверка:
`ctest --test-dir build -R writer_queue --output-on-failure`.

Глубины GPU-очередей нельзя увеличивать произвольно: на проверенном GPU NVDEC
отклонил запрос 36 поверхностей. GPU fixture из 10 кадров проверен с очередями
10/10, обычный CLI использует 8/8. Часть поверхностей нужна самому decoder;
резерв зависит и от исходного codec. См. [реализацию NVDEC в FFmpeg](https://ffmpeg.org/doxygen/6.0/nvdec_8c_source.html).

При ошибке чтения CLI также завершает
полученную запись и возвращает ненулевой код. Для RTSP-записи переподключение
включается явно:

```sh
./build/camera_demo --queue-depth 4 --reconnect 3 --transcode "$RTSP_URL" tmp/live.mp4
```

`RTSP_URL` задай в своём терминале; не сохраняй пароль камеры в репозитории.
`--reconnect N` ограничивает дополнительные попытки открытия/чтения за весь запуск;
по умолчанию их нет. Паузы — 1, 2, 4, затем максимум 5 секунд. Ctrl+C прерывает
паузу. После обрыва Writer завершает текущий MP4, Video уничтожается с join,
новая сессия получает новые Video и Writer. Файлы: `live.mp4`, `live_session2.mp4`,
`live_session3.mp4`; существующие дополнительные файлы пропускаются. Первый файл,
как и прежде, перезаписывается. Попытка без кадров может не создать файл, поэтому
номера бывают с пропусками. Timeline каждой записи независим; промежуток
разрыва не заполняется. Ошибка Writer останавливает программу без повторной попытки.
Исчерпание попыток возвращает код 1; пользовательская остановка — 0.
